[NSDI'24] MegaScale: Scaling Large Language Model Training to More Than 10,000 GPUs 论文阅读

发表于 2026-11-27 分类于 llmsys 阅读次数： 本文字数： 6.1k 阅读时长 ≈ 22 分钟

论文：MegaScale: Scaling Large Language Model Training to More Than 10,000 GPUs（NSDI’24）

作者：Ziheng Jiang、Haibin Lin（字节跳动，共同一作）、Yinmin Zhong（北京大学，共同一作）、Qi Huang、Yangrui Chen、Zhi Zhang、Yanghua Peng 等（字节跳动），Xin Jin（北京大学），Xin Liu（字节跳动）

代码：volcengine/veScale

#摘要

将大语言模型（LLM）训练扩展到一万张以上 GPU，给系统的训练效率（MFU）与长期稳定性（Stability）带来了前所未有的挑战：单个任务独占上万张卡连续运行数周，不仅通信、算子、数据加载和网络拥塞处处消耗吞吐，硬件故障、网卡闪断与隐蔽的计算慢节点（Straggler）更是常态，任何一个慢节点都会拖慢整座万卡集群。

MegaScale 围绕两条核心系统原则构建万卡生产训练体系：

  1. 算法—系统全栈协同设计（Algorithm-System Co-design）：打通模型结构与优化器（并行 Transformer 块、滑动窗口注意力、LAMB 扩大 Batch 削减流水线气泡）、3D 并行通信与计算精细重叠、算子融合、单机共享内存数据流水线、无全局屏障的秒级通信组初始化，以及多轨 CLOS 网络拓扑与混合拥塞控制；
  2. 深度可观测性（In-depth Observability）：构建基于富心跳的自动故障定位与两阶段快速 Checkpoint 恢复框架，并研发零同步开销的常驻 CUDA Event 监控器（全集群热力图 + 分布式统一时间线 + 3D 并行依赖拓扑视图）精准揪出概率性挂死与慢节点。

在 12,288 张 Ampere GPU 上训练 175B 模型时，MegaScale 取得了 55.2% 的 MFU，相比开源基线 Megatron-LM 提升 1.34×（41.2% → 55.2%）；在数周的百亿/千亿参数万卡真实生产任务中，成功自动定位并恢复 100 余次软硬件故障，保持超过 90% 的有效训练时间占比（ETTR）。

#1. 背景：3D 并行训练底座

面对单卡显存放不下、单机算力跑不完的大模型，现代预训练普遍组合三种正交的并行维度：

  • 数据并行（DP）与 ZeRO-2：如图 1 所示，传统 DP 在每份副本上重复存储全部状态并在反向结束后做 All-Reduce；而常用的 ZeRO-2 将优化器状态与梯度按 DP 组切分，从而把原来的梯度 All-Reduce 拆解为反向阶段的 Reduce-Scatter（聚合梯度分片）与参数更新后的 All-Gather（拉取最新参数分片），在不增加总通信量的前提下大幅省显存。

  • 流水线并行（PP）与交错式 1F1B：按层切分模型，并将一个全局 Batch 拆成多个微批次（Micro-batch）流水执行。如图 2 所示，Megatron-LM 采用交错式 1F1B（Interleaved 1F1B）调度——每张卡（物理 Stage）负责多个不相邻的「虚拟阶段 / 模型块（Model Chunk）」（图 2 中 3 个物理 Stage 各托管 2 个虚拟块），依次经历 Warm-up（仅前向填充流水线）、Steady 1F1B（一前向配一反向）与 Cool-down（排空剩余反向）三个阶段，将流水线气泡比例压缩虚拟阶段倍数vvv。

  • 张量并行（TP）与序列并行（SP）：TP 在层内切分 Attention 和 MLP 的大矩阵乘（GEMM），通信极其密集，必须限制在单机 NVLink 内部；SP 则将 LayerNorm、Dropout 等计算轻但激活显存大的算子沿序列维度切分，配合 TP 的 All-Gather / Reduce-Scatter 进一步消除重复激活显存。跨机通信时，MegaScale 优先组建 DP 组而非 PP 组，以减少数据并行跨 Mini-pod 的通信跳数。

#2. 万卡规模的高效训练优化（全栈协同）

#2.1 算法层等价改造

在不损失千亿参数模型最终收敛精度的前提下（§5.2 实验验证），MegaScale 引入三项算法改造来打开系统并行空间：

  1. 并行 Transformer 块（Parallel Transformer Block, PTB）：参照 PaLM 与 GPT-J，将标准串行残差公式

    y=x+MLP(LN(x+Attention(LN(x))))y = x + \text{MLP}(\text{LN}(x + \text{Attention}(\text{LN}(x))))y=x+MLP(LN(x+Attention(LN(x))))

    改写为 Attention 与 MLP 并行分支的形式：

    y=x+MLP(LN(x))+Attention(LN(x))y = x + \text{MLP}(\text{LN}(x)) + \text{Attention}(\text{LN}(x))y=x+MLP(LN(x))+Attention(LN(x))

    两者共享同一个前置 LayerNorm 输出，消除了层内 Attention 到 MLP 的串行依赖，显著缩短单层计算关键路径；
  2. 滑动窗口注意力（Sliding Window Attention, SWA）：用窗口大小w≪sw \ll sw≪s 的局部注意力替代全序列自注意力，将复杂度从O(s2)\mathcal{O}(s^2)O(s2) 降至O(s⋅w)\mathcal{O}(s \cdot w)O(s⋅w)，依靠深层堆叠维持全局感受野；
  3. LAMB 优化器放大全局 Batch Size：大规模强扩展最怕受收敛性限制无法继续放大 Batch Size，导致微批次mmm 太少、PP 气泡占比过高。实验表明 LAMB 可将 LLM 的全局 Batch Size 放大 4 倍而不损收敛精度，从而显著拉长交错 1F1B 的稳态阶段并摊薄气泡开销（注：论文 3.1 节原文将「1×1\times1× Batch 跑 4 步」与「4×4\times4× Batch 跑 1 步」的气泡分别写为4vp−1m\frac{4}{v}\frac{p-1}{m}v4​mp−1​ 和1vp−14m\frac{1}{v}\frac{p-1}{4m}v1​4mp−1​ 并得出减少 87.5%，此处把单步气泡占比p−1vm\frac{p-1}{vm}vmp−1​ 与 4 步的绝对步数混乘了——无论按单步气泡占比p−1vm→p−14vm\frac{p-1}{vm} \to \frac{p-1}{4vm}vmp−1​→4vmp−1​ 算，还是按处理相同 token 数的总绝对气泡时间4p−1v→1p−1v4\frac{p-1}{v} \to 1\frac{p-1}{v}4vp−1​→1vp−1​ 算，4×4\times4× Batch 实际削减的流水线气泡均为1−14=75%1 - \frac{1}{4} = 75\%1−41​=75%）。

#2.2 3D 并行的极致通信—计算重叠

MegaScale 对 DP、PP、TP/SP 三个维度的通信依赖做了逐一拆解，把所有非关键路径通信藏进计算背后：

（1）TP / SP 通信拆块融入 GEMM 流水（图 3）

如图 3a 所示，引入 PTB 后，前向入口的 SP All-Gather 和出口的 TP Reduce-Scatter 原本卡在关键路径上。得益于 Attention 分支与 FFN（MLP）分支现在可以并行执行，且 FFN 分支的 GEMM 计算量更大，MegaScale 把 All-Gather 和 Reduce-Scatter 融合进 FFN 路径的列并行/行并行线性层中（图 3b），再将大矩阵乘拆成NNN 个小分块（图 3c）：

  • 前向 ColParaLinear with AG：主流（Stream S0）一边算已就绪输入分块A0×WA_0 \times WA0​×W，通信流（Stream S1）同时异步拉取后续分块 Copy A1 ... AN；前向 All-Gather 的完整结果随即复用于旁路的 QKV 投影；
  • 前向 RowParaLinear with RS：主流刚算出一块部分和B×W0B \times W_0B×W0​，通信流立刻异步启动该块的 Reduce-Scatter C0，与后续 GEMM 分块B×W1B \times W_1B×W1​ 完全重叠；反向传播同理对称处理。

（2）PP 点对点通信解耦 Send 与 Receive（图 4）

常规实现常把相邻 Stage 间的 Send/Recv 绑成成对的联合调用（S/R），容易被较慢的一方阻塞在关键路径上。MegaScale 按阶段精细解耦依赖：

  • Warm-up 阶段（图 4 左）：当前 FWD 只依赖上一次 Recv 拿到的激活，而本次算完发往下游的 Send 与本卡紧接着的下一次 Recv + FWD 并无依赖——拆到独立 CUDA Stream 后，Send 可与后续前向计算完全重叠（Cool-down 阶段作为逆过程同理）；
  • Steady 1F1B 阶段（图 4 右）：某次反向 BWD 前面的 Recv 其实是为再下一次 FWD 预取激活，而它触发的梯度 Send 是给上游 Stage 用的——因此 Send 和 Recv 都与本卡紧邻的计算解耦，可双双异步发起、完全隐藏在 FWD/BWD 计算时间内。

（3）DP（ZeRO-2）按虚拟模型块预取与优先级调度

在交错 1F1B 下，每张卡托管 vpp_size 个模型块，DP 的参数 All-Gather 在每个模型块前向之前触发，梯度 Reduce-Scatter 在其反向之后触发。唯一藏不住的原本是整步第一个模型块的 All-Gather 和最后一个 Reduce-Scatter。MegaScale 借鉴 PyTorch FSDP，在每步最开头提前预取首个模型块的 All-Gather，让它与数据加载重叠，直接省去12×vpp_size\frac{1}{2 \times \text{vpp\_size}}2×vpp_size1​ 的暴露通信；同时按照下游计算算子对通信结果的依赖先后顺序，为并发通信算子赋予不同优先级，优先跑急需的数据。

#2.3 高效算子与树形共享内存数据流水线

  • 算子融合：注意力采用 FlashAttention-2 改善 Thread Block 与 Warp 间的工作切分；将原本碎成多个小 Kernel 的 LayerNorm 和 GeLU 做算子融合，减少 Kernel Launch 开销与全局显存往返读写。
  • 异步数据预处理 + 单机共享内存去重加载：一方面，在上一步末尾 GPU 同步梯度时就提前异步启动下一步的 CPU 数据预处理；另一方面，观察到单机 8 张 GPU 同属一个 TP 组，每轮迭代读取的训练样本本来就完全相同！传统做法让每张卡各自起 DataLoader 进程抢磁盘带宽纯属浪费。MegaScale 改为两层树形加载：每台物理机只起唯一一个专用 DataLoader 将数据读入主机共享内存（Shared Memory），本机 8 个 GPU Worker 直接从共享内存拷入显存，彻底消除了单机冗余磁盘 I/O 争用。

#2.4 万卡通信组秒级初始化：从 1047 秒压到 5 秒内

在小规模集群里毫不起眼的 torch.distributed 建组开销，到了数千上万张卡会变成灾难：实测原生 Megatron-LM 在 2,048 张 Ampere GPU 上仅初始化 NCCL 通信组就要 1,047 秒（超过 17 分钟），严重拖慢日常调试与故障重启恢复。剖析定位出两大病灶：

  1. 单线程阻塞的 TCPStore：PyTorch 默认用内置的 TCPStore 做建组末尾的同步屏障，单线程阻塞读写在千卡并发下严重排队。将其替换为非阻塞异步的 Redis 后，2,048 卡建组时间从 1,047s 降到 361s；
  2. 滥用O(n2)\mathcal{O}(n^2)O(n2) 全局屏障（Global Barrier）：原先每建完一个子通信组，所有进程都要执行一次全局屏障。通过精心重排各并行维度通信组的创建顺序、消去不必要的全局同步，同步复杂度从O(n2)\mathcal{O}(n^2)O(n2) 降至O(n)\mathcal{O}(n)O(n)。

两招叠加后，2,048 卡初始化压到 5 秒以内，超过 10,000 卡的初始化也控制在 30 秒以内。

#2.5 数据中心网络拓扑与 RoCE 调优

MegaScale 针对万卡 3D 并行流量特征定制了底层 RDMA 网络：

  • 三层 1:1 无收敛 CLOS 与多轨（Multi-rail）拓扑：基于单芯片 25.6Tbps（64×400Gbps）的 Broadcom Tomahawk 4 交换机构建三层 CLOS，上下行带宽比严格 1:1（32 下行 : 32 上行）。为降低 ECMP 哈希冲突，在 ToR（接入层）交换机侧用定制 AOC 线缆将 1 个 400G 下行口一分为二成 2 个 200G 口（使单条上行链路带宽是下行的两倍，降低拥塞概率）；每台服务器配备 8 张 200G RNIC，按多轨方式分别连向 8 台不同 ToR 交换机，同一组 ToR 下可直连多达 64 台服务器（512 卡）。调度器尽量把通信最密集的节点（如同一 DP/PP 紧耦合域）紧凑放置在同组 ToR 下以减少跳数。
  • 融合 Swift 与 DCQCN 的拥塞控制：大规模 All-to-All / 集合通信下，默认 DCQCN 极易触发过量 PFC（优先级流控）暂停帧并引发队头阻塞（HoL Blocking）。MegaScale 将 Google Swift 的精准端到端 RTT 延迟测量与 DCQCN 基于 ECN 标记的快速降速结合，大幅压低 PFC 触发并提升有效吞吐。
  • 自适应重传应对链路闪断：调优 NCCL 重传定时器与重试次数（调大超时阈值，避免几秒钟的瞬时网卡闪断直接让训练报错崩溃），并开启网卡硬件 adap_retrans 特性缩短短周期抖动后的重传恢复间隔。

#3. 自动化容错与两阶段快速恢复

在万卡规模下不能靠人工救火。如图 5 所示，MegaScale 设计了一套由中心 Driver 与每节点 Executor + 守护进程组成的闭环容错框架：

  1. 富心跳与毫秒级/秒级双层监控（§4.2）：每个节点的守护进程周期性向 Driver 发送富心跳，不仅包含机器/Pod 状态，还实时聚合过滤训练进程的 stdout/stderr 错误关键字，并上报 RDMA 网卡流量指标——有些静默挂死（Hang）不会抛异常，但周期性的训练步 RDMA 流量会骤降或归零，Driver 据此自动告警或直接触发恢复。外围还配有秒级（查 ECN/PFC/QoS 配置与端口闪断）和毫秒级（查瞬时拥塞与 DP/PP 带宽是否触顶）两级监控。
  2. 轻量级全量自检诊断（§4.3）：一旦心跳超时或检测到异常，Driver 暂停全集群任务，下令所有节点并发跑一套几分钟内就能完成的轻量自检，平衡「排查耗时」与「误杀好机器」：
    • 机内网络测试：一是 Loopback 满网格测试，测所有 RNIC 到本机各 NUMA 内存节点与各 GPU 的环回带宽，揪出 PCIe 降速或拓扑配置异常；二是 RNIC-to-RNIC 测试，检验同机网卡间连通性与路由配置；
    • 两级 NCCL 测试：先跑单机内 GPU All-to-All，通过后再与同 ToR 下的邻居机器跑跨机 All-Reduce。定位出坏节点后，Driver 将故障 IP 拉黑并提交给定制 Kubernetes 驱逐故障 Pod、自动补齐通过自检的健康备机。
  3. 两阶段异步 Checkpoint 与去重广播恢复（§4.4）：
    • 保存阶段：第一阶段各 GPU Worker 借助优化后的序列化与 Pinned Memory，经高速 PCIe 在数秒内将片上状态写入主机内存，随即立刻继续下一步训练；第二阶段由后台独立进程异步将主机内存快照刷入远端分布式文件系统（HDFS）。
    • 恢复阶段：加载在关键路径上，若上万张卡同时去读 HDFS 会瞬间打爆存储带宽。由于同一 DP 组（或共享分片组）内的多个 Worker 持有完全相同的参数与优化器分片，MegaScale 指定每组仅由单个代表 Worker 从 HDFS 读取一次，随后利用高速 GPU 计算网络广播（Broadcast）给组内其余 Worker，将 HDFS 读取负载线性降低数倍（这一思路后来进一步演化为支持任意弹性并行度重切分的 ByteCheckpoint（NSDI’25））。

#4. 深度可观测性：揪出隐蔽慢节点与静默挂死

自检能抓出 90% 以上的明确故障，但最棘手的是两类「带病运行」问题：概率性卡死与慢节点（Straggler）导致的 MFU 不一致和缓慢衰减（如图 6 所示，完全相同的配置在不同轮次启动时峰值 MFU 高低不一，且随着步数推进从 ~0.42 一路掉到 ~0.32，而单卡跑 GEMM 微基准却一切正常）。

为此，MegaScale 开发了生产全程常开、开销可忽略的三大诊断视图：

#4.1 基于 CUDA Event 的常驻监控器：热力图与分布式时间线

传统 PyTorch Profiler 或手写计时器依赖 cudaStreamSynchronize，一开就会严重拖慢训练，无法在线上常驻。MegaScale 改用异步 CUDA Event 记录关键代码段起止耗时，逐行写入本地日志后由独立 Streamer 进程实时推入 Kafka、落库远端分析型数据库。

  • 全集群热力图（图 7）：汇总各卡前反向平均计算耗时并以颜色深浅展示。热力图一举揭开了「不同轮次 MFU 不一致」的谜底：集群里大约有 0.5% 的物理机前向计算比正常机器慢约 10%（如 host 8 的 rank 32、host 10 的 rank 40/41），因为每次作业调度分到的机器带有随机性，一旦抽中这批慢机器就会木桶效应拖垮全集群。剔除这批慢主机后，不仅跨轮次 MFU 恢复一致，整体 MFU 还直接提升了 0.7%。

  • 分布式统一时间线（图 8）：将跨节点的整个 PP 组、DP 组或 TP 组的 Trace Span 对齐到同一根时间轴上，直观呈现微批次流转、流水线气泡与跨机同步等待关系。

#4.2 3D 并行拓扑故障定位视图

当万卡集群中某一张坏卡在执行 NCCL 通信时概率性卡死，所有依赖它的上下游节点都会级联阻塞，最终成千上万个进程同时刷屏报 NCCL timeout，根因彻底淹没在超时洪水中。

MegaScale 的解法非常实战：让每个 Worker 在通信超时退出前记录自己当前卡在哪一个通信事件上，并根据 3D 逻辑拓扑画出有向数据流依赖图（如图 7 中选中 rank 20 展开的三维通信边）。关键判据在于——被别人拖累而超时的正常节点退出前都会留下日志，唯独真正彻底 Hang 死的源头坏卡进程连日志都打不出来！顺着超时节点的等待方向一查哪个上游节点「沉默无日志」，几秒钟就能精准锁定罪魁祸首并手动隔离下线。

#5.2 生产万卡任务收敛与排障实战

图 11 展示了一次在超过 10,000 张 GPU 上持续数周、训练数千亿参数与数万亿 Token 的真实生产任务：期间经历了 100 多次训练重启（图中每次变色即一次恢复），超过 90% 的软硬件异常由容错框架全自动发现、隔离并恢复——故障检测加自检平均耗时 不到 10 分钟，从最新 Checkpoint 追平崩溃前进度 不到 15 分钟，全程有效训练时间率保持在 90% 以上，Loss 平滑收敛。

除了前文提到的 0.5% 硬件计算慢节点和网卡/AOC 光模块信号质量引发的端口闪断外，论文 6.3 节分享的「MFU 随步数缓慢下滑」破案过程堪称分布式性能调优教科书：

  1. 排除计算变慢：查 CUDA Event 监控发现，虽然每步总耗时越跑越长，但前向、反向、优化器本身的纯 GPU 计算耗时稳如泰山——说明多出来的时间全花在了集合通信等待上；
  2. 逆向锁定同步点：倒查每步最后一道集合通信——DP 梯度 Reduce-Scatter；同时监控显示网络物理带宽并无退化，说明不是传得慢，而是各 Rank 发起 Reduce-Scatter 的时间点出现了参差（Skew）；
  3. 缩微复现发现「交替漂移发散」：在每个 DP 组仅 2 个 Rank 的缩微实验中测量发起时刻，惊讶地发现并不是某个固定慢节点一直落后，而是 Rank A 与 Rank B 交替领先/落后，且两者之间的时间差振幅随步数累积越拉越大——而集合通信每次都得等最慢的那个，导致单步耗时单调递增；
  4. 定位根因并根治：顺藤摸瓜回溯到前向阶段，发现根因是关键路径上混入了不规则触发的 Python 垃圾回收（GC）以及部分耗时抖动的 PyTorch 操作。不同进程 GC 触发时机微小的不同步在数万步迭代和流水线依赖中被不断放大共振。统一管控 GC 并清理抖动代码段后，跨轮次、长达 3 万步的 MFU 曲线彻底拉成了一条水平直线（论文图 12）。

#读后总结

MegaScale 是工业界第一篇把「万卡预训练底座」从模型结构、并行调度、宿主 I/O、RDMA 交换机一路摊开讲到故障自检和线上排障的全景式系统论文。读完感触最深的三点：

  1. 到万卡规模后，性能指标不再只是峰值 MFU，而是「积分面积」（MFU×ETTR\text{MFU} \times \text{ETTR}MFU×ETTR）。单靠算子和通信重叠把峰值 MFU 推高十几个点只赢了一半；如果每次建组要 17 分钟、每次读 HDFS 恢复要半小时、混进一台慢 10% 的机器或一次 Python GC 漂移就把全集群拖慢 20%，几周跑下来浪费的算力远超算子优化省下的时间。把秒级 Redis 建组、毫秒级网络监控、两阶段 Checkpoint 和常驻无损 CUDA Event 打造成基础设施标配，才是生产系统的真正护城河；
  2. 「谁没打日志谁就是真凶」与逆向排查法非常实用。在万卡 NCCL Timeout 风暴里靠超时反向追踪沉默节点，以及通过「计算耗时恒定 + 网络带宽恒定 → 必然是集合通信到达时刻发散 → Python GC 抖动共振」的推理链，都是只有真正在大规模集群里摔打过才能提炼出的排障直觉；
  3. 与后续系统演进的脉络清晰可辨。论文 4.4 节里的两阶段 Checkpoint + DP 组代表读取广播，假设的还是恢复前后并行度不变；当剔除坏机后想用剩余机器弹性续训、或者跨阶段切分给后训练（如 HybridFlow（EuroSys’25））时，就自然引出了 ByteCheckpoint（NSDI’25） 的在线 Resharding 与树形 gRPC 控制面。
