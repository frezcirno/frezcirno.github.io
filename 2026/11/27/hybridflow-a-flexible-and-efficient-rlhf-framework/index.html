论文：HybridFlow: A Flexible and Efficient RLHF Framework（EuroSys’25）

作者：Guangming Sheng（香港大学）、Chi Zhang、Zilingfeng Ye、Xibin Wu、Wang Zhang、Ru Zhang、Yanghua Peng、Haibin Lin（字节跳动）、Chuan Wu（香港大学）

代码：volcengine/verl

#摘要

基于人类反馈的强化学习（RLHF）被广泛用于大语言模型（LLM）对齐。传统强化学习可以建模为一个数据流图（DAG）：每个节点代表一个神经网络的计算，每条边代表网络之间的数据依赖。而在 RLHF 中，数据流图显著复杂化——每个节点膨胀为一个分布式的 LLM 训练或自回归生成程序，每条边则变成异构并行策略之间的多对多组播（many-to-many multicast）。

传统 RL 框架采用单控制器（Single-Controller）统一调度节点内计算与节点间通信，但面对算子规模庞大的分布式 LLM 计算时会产生严重的控制分发开销；现有 RLHF 系统转而采用多控制器（Multi-Controller）范式，却把分布式计算与跨模型点对点通信深度嵌套在一起，难以灵活扩展新算法与新放置策略。

HybridFlow（开源实现即 verl）将两种范式分层结合：

  • 混合编程模型与分层 API：节点间用单控制器编排全局数据流与数据重切分，节点内用多控制器执行高效分布式 LLM 计算，彻底解耦模型计算与跨模型数据依赖；
  • 3D-HybridEngine：针对计算占比最高的 Actor 模型，重新设计生成阶段的并行分组方式，在训练与生成阶段切换时实现零显存冗余并大幅削减权重重切分通信量；
  • 自动设备映射（Auto-Mapping）算法：根据集群规模与模型负载，自动搜索各模型的共置/分离放置方案与最优并行度。

在 7B–70B 模型、8–128 张 A100 GPU 上的实验表明，HybridFlow 在 PPO、ReMax、Safe-RLHF 等多种算法下的端到端吞吐相比 DeepSpeed-Chat、OpenRLHF、NeMo-Aligner 提升 1.53×–20.57×。

#1. 背景与动机

#1.1 RLHF 数据流与算法多样性

在大模型预训练和监督微调（SFT）之后，RLHF 利用人类偏好数据进一步对齐模型行为。一个典型的 RLHF 系统包含多个 LLM（如 Actor、Critic、Reference Policy 和一或多个 Reward/Cost Model），其单次迭代可拆解为三个阶段：

以最常用的 PPO（图 1a）为例：

  1. 阶段 ① 生成（Generation / Rollout）：Actor 模型接收一批 Prompt，通过自回归解码生成 Response；
  2. 阶段 ② 经验准备（Preparation）：把 Prompt 与生成的 Response 分别喂给 Critic（算状态价值 Value）、Reference Policy（算参考对数概率以约束 KL 散度）和 Reward Model（算偏好奖励分），三者均只需一次前向传播（Inference）；
  3. 阶段 ③ 学习更新（Learning / Training）：结合前两阶段产出的轨迹数据计算优势函数（Advantage），通过前向、反向传播与 Adam 优化器更新 Actor 和 Critic 的权重。

不同对齐算法虽然大体遵循三阶段骨架，但模型组成与数据依赖差异很大：

  • Safe-RLHF（图 1b）：引入额外的 Cost Model 评估安全性，并在阶段 ③ 为 Actor 增加一项预训练数据集上的辅助损失Lptx\mathcal{L}_{\text{ptx}}Lptx​；
  • ReMax（图 1c）：省掉了占显存很大的 Critic 模型，但需要在阶段 ① 让 Actor 额外跑一次贪心解码（do_sample=False）作为方差缩减基线；
  • 此外还有 RLAIF、GRPO 以及将 Reward Model 替换为代码沙箱或数学判题器的推理强化学习变体。这些算法演进要求框架具备灵活表达任意 RLHF 数据流图的能力。

#1.2 分布式控制范式的两难

在分布式机器学习中，控制流组织主要有两种范式：

  • 单控制器（Single-Controller）：由一个中心控制器掌握全局硬件视图和数据流图，统一向各个 Worker 派发任务并协调执行顺序（如 RLlib Flow）。优势是可以用单进程脚本直观写出全局逻辑，灵活映射设备资源；劣势是当数据流节点内部包含数以十亿计参数的 LLM 算子时，中心控制器的逐算子派发延迟会随集群规模急剧放大。
  • 多控制器（Multi-Controller / SPMD）：每张 GPU 拥有独立的控制器进程，各自运行同一份程序，CPU 直接经高速 PCIe 向本地 GPU 下发算子（如 Megatron-LM、MegaScale、vLLM），节点内计算几乎没有调度开销。但如图 2a 所示，现有 RLHF 框架连跨模型协调也用多控制器实现：用户必须在每个模型的 SPMD 循环里手写集合通信（黑色代码）与跨模型点对点收发（蓝色 send_critic / recv_actor 代码）。计算逻辑与数据依赖深度耦合，改一个上游节点就得同步修改所有下游节点的收发逻辑，极难复用与维护。

#1.3 RLHF 负载的三大系统特征与现有框架局限

除了算法多变，RLHF 在执行层还有三个鲜明特征：

  1. 模型间负载高度异构：Actor 既要做自回归生成又要做训练；Critic 做前向推理与训练；Reference 和 Reward Model 只做单次前向推理（只需存参数，无需梯度和优化器状态）。而且实践中常拿小 Actor（如 7B）配大 Critic/Reward（如 70B）来提升对齐质量，各模型理应采用不同的并行策略。
  2. Actor 训练与生成的计算特性失衡：Actor 的生成与训练占了单步 RLHF 绝大部分耗时（在 HybridFlow 中也占到 58.9%）。训练是计算密集型，往往需要更大的模型并行度（MP = TP × PP，例如 8 卡切 8 份）来分摊激活与优化器显存；自回归生成则是访存受限型，沿用训练的大 MP 会导致每卡计算严重不饱，改用「较小 MP + 较大数据并行（DP）」（如 TP=2、复制 4 份）才能打满吞吐。但两阶段并行度不同意味着每轮迭代都要做运行时权重重切分（Resharding）——以 70B Actor 为例，每步需搬运 140GB 半精度权重，在分离部署下最高占到单步总时间的 36.4%。
  3. 多样化的模型放置（Placement）需求：如图 3 所示，把无数据依赖的模型放到不同机器上（如机器 B 跑 Critic、机器 C 共置 Ref 与 RM）可以并行执行，但阶段切换时会产生设备空闲气泡（图 3 中 Actor 与 Critic 分离部署虽能并行训练，却在其他阶段各自闲置约 1/3 的时间）；把模型共置（Colocate）在同一组 GPU 上时分复用能消除阶段气泡，但受显存容量制约，且在大集群固定全局 Batch Size 时会因 DP 过大导致单卡 Batch 过小、通信占比飙升。

论文表 1 对比了三款代表性开源 RLHF 系统的设计取舍：

核心洞察其实很清晰：RLHF 数据流图本身只有寥寥几个节点，在节点间用单控制器转发控制消息的开销相对于动辄数秒的 LLM 计算完全可以忽略，却能换来全局编排与资源虚拟化的极致灵活性；而在节点内部继续用多控制器封装分布式训练与推理引擎，就能保留底层引擎原本的计算效率。

#2. 系统架构概览

如图 4 所示，HybridFlow 由三大核心模块构成：

  1. 混合编程模型（Hybrid Programming Model，§3）：向上提供 ParallelWorker 基类（节点内多控制器分布式计算）、Transfer Protocol（节点间多对多数据重切分）与 ResourcePool（物理 GPU 虚拟化与共置/分离映射）；
  2. 3D-HybridEngine（§4）：专为 Actor 模型设计，支持训练与生成使用各自最优的 3D 并行配置，并在同一组设备内完成零冗余、低通信量的参数重切分；
  3. 自动映射算法（Auto Mapping，§5）：运行在启动前，根据用户输入的模型规格、数据流图与集群配置，结合解析模拟器自动产出最优的模型放置方案与各阶段并行度元组(p,t,d)(p, t, d)(p,t,d)。

#3. 混合编程模型与分层 API

#3.1 节点内封装与节点间传输协议

节点内：封装分布式计算程序。HybridFlow 提供 3DParallelWorker、FSDPWorker、ZeROWorker 等多控制器基类。如图 5a 所示，给定分配好的 ResourcePool 与并行配置(p,t,d)(p, t, d)(p,t,d)，基类负责建立对应的 TP/PP/DP 通信组并初始化分片权重。在其之上派生出 Actor、Critic、Reference、Reward 等模型子类，暴露高层原语 API——例如 ActorWorker 提供 generate_sequences、compute_log_prob、compute_loss、update_actor，内部直接复用 Megatron-LM、PyTorch FSDP、DeepSpeed 或 vLLM 的成熟计算逻辑，不包含任何跨模型收发代码。

节点间：用传输协议统一多对多数据重切分。当上游模型与下游模型采用不同的并行切分跑在不同（或相同）GPU 集合上时，中间数据（Prompt、Response、Log-prob、Advantage 等，封装为基于 TensorDict 的 DataProto）需要做多对多重切分。HybridFlow 通过 @register(transfer_mode=...) 装饰器为每个模型方法绑定一套传输协议（Transfer Protocol），每个协议由一对 collect（聚合源端输出引用）和 distribute（按目标端并行度切分并派发输入引用）函数组成。

以图 5b 中 Actor（(p,t,d)=(1,2,3)(p,t,d)=(1,2,3)(p,t,d)=(1,2,3)，共 6 卡）向 Critic（(p,t,d)=(2,1,2)(p,t,d)=(2,1,2)(p,t,d)=(2,1,2)，共 4 卡）传递生成结果为例，两者均绑定 3D_PROTO：

  • 在 3D 并行中，模型输出只存在于最后一个流水线阶段（p=−1p=-1p=−1），且在同一 TP/PP 组内语义重复，因此 3D_PROTO 的 collect 只从每个 DP 组的(p=−1,t=0)(p=-1, t=0)(p=−1,t=0) Worker 收集数据引用（Ray Data Future）汇总到单控制器（步骤 ①–③）；
  • 单控制器发起对 Critic 的异步调用，并通过 Critic 的 distribute 函数把对应切片的 Future 分发给 Critic 的各个 DP 组并组内广播（步骤 ④–⑤）；
  • Critic 的每张 GPU 根据拿到的 Future，直接点对点向源端 GPU 拉取自己所需的那一份本地 Batch 数据（步骤 ⑥）。

注意这里的精妙之处：单控制器只经手轻量的元数据与 Future 引用，真正的张量数据直接在源/目 GPU 进程之间传输，因此中心控制器绝不会成为数据面带宽瓶颈。系统内置了 ONE_TO_ALL、3D_PROTO、3D_ALL_MICRO_DP、DP_PROTO 等 8 种传输协议，覆盖了绝大多数切分组合。

资源池与异步数据流执行。ResourcePool 将一组物理 GPU 虚拟化：把同一个 ResourcePool 实例传给多个模型，它们就会共置在这组 GPU 上并按控制器调用顺序串行时分执行（防止并发 OOM）；传入不同的 ResourcePool 实例（彼此不重叠），模型就会部署在不同 GPU 子集上。借助 Future 机制，分离部署的无依赖节点（例如阶段 ② 的 Reference、Reward 和 Critic 前向）只要上游 Future 就绪便会自动并发触发执行，无需改动一行算法脚本。

#3.2 数行代码实现多种 RLHF 算法

得益于计算与通信的彻底解耦，用户只需在单控制器进程中写几行顺序 Python 代码即可拼装不同算法（图 6）：

  • PPO 核心循环仅需 8 行代码（生成序列 → 算 Value / Ref Log-prob / Reward → 在控制器本地算 Advantage → 更新 Critic 与 Actor）；
  • 切换到 Safe-RLHF：直接复用 RewardWorker 类实例化一个 cost 模型，在循环里加 5 行代码计算安全代价与预训练损失即可；
  • 切换到 ReMax：加一行贪心生成调用，删掉 Critic 的两行调用即可；
  • 对于数学推理或代码生成场景（如 GRPO），只需把神经网络 Reward Model 替换成包装了沙箱判题或规则校验的远程函数，外层编排逻辑同样保持不变。

#4. 3D-HybridEngine：零冗余 Actor 训推切换

#4.1 训练并行组与生成 Micro-DP 组

为了避免像 OpenRLHF 那样维护两份独立的 Actor 权重，HybridFlow 让 Actor 的训练和生成运行在同一组NaN_aNa​ 张 GPU 上，分时复用同一份权重。设训练阶段的 3D 并行度为p-t-dp\text{-}t\text{-}dp-t-d（分别代表 PP、TP、DP 大小），而生成阶段由于访存受限，通常需要更小的模型并行度pg,tgp_g, t_gpg​,tg​ 和更大的数据并行度。

为此，3D-HybridEngine 在生成阶段保持原有的ddd 个训练 DP 组不变，同时将每个训练模型并行组（共p×tp \times tp×t 张卡）进一步裂变为dgd_gdg​ 个微数据并行组（Micro-DP Group），形成四维生成并行配置pg-tg-dg-dp_g\text{-}t_g\text{-}d_g\text{-}dpg​-tg​-dg​-d，满足：

  1. All-Gather 聚合生成权重（步骤 ①）：在第i+1i+1i+1 轮开始时，每个 Micro-DP 组内部通过 All-Gather 拼出生成所需的模型参数分片；
  2. 分发 Prompt（步骤 ②）：按扩大后的总生成副本数dg×dd_g \times ddg​×d 加载并切分 Prompt 微批次；
  3. 自回归生成与结果汇聚（步骤 ③）：调用分布式 vLLM 引擎并发生成 Response，随后在每个 Micro-DP 组内做一次 All-Gather，使同一训练 MP 组内的卡重新持有相同的轨迹数据；
  4. 切回训练权重视图（步骤 ④）：释放生成期的额外分片，恢复为训练阶段的p-t-dp\text{-}t\text{-}dp-t-d 权重划分；
  5. 模型更新（步骤 ⑤）：计算 RLHF 损失并更新 Actor 参数。

#4.2 零冗余并行重分组机制

如果直接沿用传统的连续 Rank 分组方式，训推切换时就会产生显存冗余与多余通信。

看图 8 的 8 卡例子：训练采用1-4-21\text{-}4\text{-}21-4-2，即训练 TP 组为 [G1, G2, G3, G4] 和 [G5, G6, G7, G8]，每张卡持有1/41/41/4 权重；生成采用1-2-2-21\text{-}2\text{-}2\text{-}21-2-2-2（每个生成副本只需 TP=2，即每张卡持有1/21/21/2 权重）：

  • 朴素分组（HybridFlow-V，图 8a）：按常规习惯把连续 Rank 划为生成 TP 组：[G1, G2]、[G3, G4]、[G5, G6]、[G7, G8]。注意此时生成 TP 组的第 0 号分片落在 G1 和 G3 上（需要前半部分权重，即原 G1+G2 的分片），第 1 号分片落在 G2 和 G4 上（需要后半部分权重，即原 G3+G4 的分片）。结果 G2 和 G3 在训练时持有的本卡权重（灰色块）与自己在生成时所需的权重毫无重叠！为了下一阶段还能继续训练，G2、G3、G6、G7 被迫在显存里额外保留那份用不上的训练权重；而且切换时必须在整个 4 卡训练 TP 组内做全量 All-Gather（峰值显存飙到完整模型MMM），再丢弃一半不用。
  • 重排生成分组（HybridFlow，图 8b）：按步长ttg\frac{t}{t_g}tg​t​ 和ppg\frac{p}{p_g}pg​p​ 跨步选取 Rank 组建生成 TP/PP 组，而把相邻 Rank 划入同一个 Micro-DP 组！在图 8b 中，生成 TP 组变为 [G1, G3]、[G2, G4]、[G5, G7]、[G6, G8]，而 Micro-DP 组变为 [G1, G2]、[G3, G4]、[G5, G6]、[G7, G8]。这样一来，G1 和 G2 在生成时都扮演各自生成副本的「前半部分 TP rank」，它们原本在训练阶段持有的1/41/41/4 权重恰好是自己生成所需1/21/21/2 权重的真子集！因此：
    1. 每张卡都能在生成阶段原地复用自己的训练权重分片，显存冗余严格降为 0；
    2. All-Gather 被严格限制在规模仅为dg=2d_g = 2dg​=2 的 Micro-DP 子组内部并发完成，既不需要跨整个训练 MP 组汇聚完整模型，也把峰值参数显存压到了生成分片大小1tgpgM\frac{1}{t_g p_g}Mtg​pg​1​M。

#5. 自动设备映射算法

混合编程模型把放置与并行度彻底参数化后，HybridFlow 用一个离线搜索算法（论文 Algorithm 1）在任务启动前自动寻找最小化单步端到端耗时的映射方案，分为外层设备放置搜索与内层并行度搜索两级：

  1. 枚举模型共置划分（Bell Partition）：对数据流图中的kkk 个模型枚举所有集合划分方案P\mathcal{P}P。例如 PPO 有 4 个模型，总共有B4=15B_4 = 15B4​=15 种放置拓扑——从 4 个模型全共置（对应 DeepSpeed-Chat）到 4 个模型完全独立分池（对应 OpenRLHF），再到各种部分共置组合（如 NeMo-Aligner 的二二分立）。
  2. 显存下界剪枝与 GPU 配额枚举：对每种划分方案中的每个「共置模型集合（Colocated Set）」，先根据模型参数、梯度、优化器状态开销算出不发生 OOM 的最小卡数下界Amin⁡A_{\min}Amin​，再枚举将集群NNN 张 GPU 分配给各个共置集合的合法整数划分AAA（最坏复杂度为整数划分O ⁣((N−1)!(k−1)!(N−k)!)\mathcal{O}\!\left(\frac{(N-1)!}{(k-1)!(N-k)!}\right)O((k−1)!(N−k)!(N−1)!​)，对k=4,N≤128k=4, N \le 128k=4,N≤128 规模极小）。
  3. 内层自动并行搜索与结果缓存（auto_parallel）：给定某个模型分到的卡数NlN_lNl​（设单机U=8U=8U=8 卡），在满足最小模型并行度下界（留足 KVCache 空间）的前提下枚举(p,t,d)(p, t, d)(p,t,d)，调用面向训练、前向推理（均受计算限制）与自回归生成（受访存带宽限制）的三个解析代价模型 simu 估算延迟。因为同一模型在相同卡数NlN_lNl​ 下的最优并行策略与外层如何组合无关，算法将其缓存复用，把最大规模（70B / 128 卡）的搜索总耗时控制在半小时以内（对比数天的实际训练完全可忽略）。
  4. 整图阶段延迟汇总（d_cost）：遍历数据流图的各个阶段iii——同一共置集合内同阶段的多个模型串行累加耗时，不同共置集合之间同阶段的模型并发取最大值，最后对所有阶段求和，选出端到端延迟最低的全局方案。

#6. 实验评估

实验平台为 16 台服务器（共 128 张 A100-80GB，机内 600GB/s NVLink，机间 200Gbps 网络），模型采用 Llama 7B / 13B / 34B / 70B，数据集为 Dahoas/full-hh-rlhf（Prompt 与 Response 长度均固定为 1024，全局 Batch Size 1024，PPO Epoch 为 1、每轮 8 次更新），对比 DeepSpeed-Chat v0.14.0、OpenRLHF v0.2.5 与 NeMo-Aligner v0.2.0。

#6.1 端到端吞吐与扩展性

几个关键现象：

  • 模型越大，HybridFlow 优势越悬殊：70B PPO 上平均加速达 9.64×。原因在于 DS-Chat 与 OpenRLHF 训练采用 ZeRO-3 带来大量跨机集合通信，且训推切换耗时极长（HybridFlow 将转换开销分别降低了最高 71.2% 和 89.1%）；而 NeMo-Aligner 因生成沿用训练大 MP 且无 KVCache，仅生成阶段就耗掉 81.2% 的迭代时间；
  • 强扩展效率达 66.8%：在全局 Batch Size 固定为 1024 的强扩展测试中，即便把 7B 扩展到 128 卡，HybridFlow 依然比最擅长大集群分离部署的 OpenRLHF 快 1.53×–1.71×。

#6.2 模型放置策略随集群规模的拐点规律

作者在 HybridFlow 内固定底层引擎，专门横向对比了 Colocate（全共置）、Split（二二分立）、Standalone（全分离）和 HybridFlow（自动映射寻优）四种放置（图 12）：

  • 中小集群（16–64 卡）：Colocate 最优。此时单模型计算足以吃满全部 GPU，全共置时分复用消除了所有阶段间的设备闲置气泡；
  • 中等偏大集群（96 卡，以及 34B 的 128 卡）：Split 反超成为最优。因为在固定全局 Batch 下，继续全共置会让 DP 过大、单卡计算/通信比恶化；把设备对半分给两组模型并发执行，缩小了各自的 DP 跨机通信域；
  • 大集群（13B 在 128 卡）：Standalone 最优，自动映射为 Actor 分配 64 卡、Critic 32 卡、Ref 与 RM 各 16 卡，最大化阶段并发度；
  • 异构模型尺寸（13B Actor/Ref + 70B Critic/RM）：64 卡以内仍是 Colocate 平均高出 44.8%；96 卡时 Split 最优；到 128 卡时，自动映射找到了一种非对称混布方案——把 13B Actor、13B Ref 和 70B RM 三者共置在 64 卡上，另外 64 卡独占跑 70B Critic，既让阶段 ② 的经验准备时间对齐以消除空闲等待，又让阶段 ③ 最重的 Actor 与 Critic 训练跨机并行。

#6.3 3D-HybridEngine 消融分析

  • 转换耗时（图 14）：相比基线，HybridFlow 平均缩短转换时间 55.2%（11.7s），在 70B / 128 卡上最高削减 89.1%（省去 78.2s），且随集群扩大几乎保持水平不变。原因在于基线汇聚全量参数时为了防 OOM 必须逐层分批收集多次，OpenRLHF 还要跨节点同步整份副本；而 HybridFlow 只需在机内 Micro-DP 小组里做一次无冗余 All-Gather。
  • 生成并行度权衡（论文图 15）：在 16 卡训练1-8-21\text{-}8\text{-}21-8-2 的设定下扫描生成 TP 大小tg∈{8,4,2,1}t_g \in \{8,4,2,1\}tg​∈{8,4,2,1}。对 7B 选tg=2t_g=2tg​=2（dg=4d_g=4dg​=4）、对 13B 选tg=4t_g=4tg​=4（dg=2d_g=2dg​=2），生成延迟相比沿用训练tg=8t_g=8tg​=8 分别下降 60.3% 和 36.4%；但继续把tgt_gtg​ 压到 1 反而变慢——因为单卡要塞下完整模型权重，挤占了原本留给 vLLM KVCache 的剩余显存，导致解码并发 Batch 受限。这也印证了显存容量与计算并行度联合搜索的必要性。

#7. 讨论与演进

论文第 9 节还讨论了几个与后续大模型后训练系统演进直接相关的方向：

  • 容错机制：单控制器天然适合通过 RPC 统一协调各 ParallelWorker 组保存检查点（包含 Actor/Critic 权重、Dataloader 偏移与 RNG 状态），也可结合参数广播或 Gemini（SOSP’23） 式的 CPU 内存快照利用存活副本快速恢复；
  • 总结出的三条放置经验法则：① 优先给无法与其他模型并行的 Actor 分更多卡以压缩最慢的生成阶段；② 算力能吃满时中小规模优先全共置；③ 强扩展到大集群时至少将 Actor 与 Critic 拆到不同设备上并行训练；
  • 从偏好对齐走向推理强化学习（Reasoning RL）：作者明确指出，除人类偏好对齐外，这套混合数据流同样适用于数学推理与代码生成（如 PPO 与 GRPO），只需去掉神经网络 Reward Model、接入沙箱或规则校验远程函数即可——这也正是开源项目 verl 后来在长思维链（CoT）后训练中被广泛采用的核心原因。

#读后总结

如果用一句话概括 HybridFlow 的设计哲学，就是「控制面集中化以换取编排自由，数据面与算子面去中心化以保住硬件效率」。

  1. 找准了单控制器与多控制器的分界线。以前大家争论 TensorFlow/Pathways 式的单控制器和 PyTorch SPMD 多控制器孰优孰劣，往往默认整个系统只用同一种范式。HybridFlow 看穿了 RLHF 图「粗粒度看只有四五个模型阶段，细粒度看每个节点是百亿参数巨兽」的两层结构——把单控制器放在模型间传 DataProto 的 Future，把多控制器留在 ParallelWorker 内部跑 Megatron/FSDP/vLLM，两边各自的短板都恰好被避开了；
  2. 3D-HybridEngine 的步长重排是一个非常漂亮的代数技巧。只靠把生成 TP 组从「连续取卡」改成「按ttg\frac{t}{t_g}tg​t​ 跨步取卡、相邻卡组合成 Micro-DP」，就让每张卡的训练分片自然成为生成分片的子集，不花一分额外显存、不做全组广播就完成了从重度模型并行到高吞吐数据并行的切换；
  3. 共置（Colocate）与分离（Disaggregate）不是非黑即白的宗教路线，而是集群规模与 Batch 约束的函数。论文用实验清晰展示了随 GPU 数量增加，最优解从 Colocate → Split → Standalone / 非对称混布 迁移的过程。不过也要看到，本文实验为了公平对比尚未考虑超长思维链生成下的长尾响应空泡（Straggler Rollout）与异步/部分离策略（Off-policy）流水——当输出长度从固定的 1024 拉长到数万 token 时，把生成池与训练池解耦并做流式样本调度，就成了下一代 RL 训练基础设施继续演进的主战场。
