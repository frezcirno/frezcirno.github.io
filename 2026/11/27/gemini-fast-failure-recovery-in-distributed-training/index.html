[SOSP'23] Gemini: Fast Failure Recovery in Distributed Training with In-Memory Checkpoints 论文阅读

论文：Gemini: Fast Failure Recovery in Distributed Training with In-Memory Checkpoints（SOSP’23）

作者：Zhuang Wang（Rice 大学，工作完成于 AWS 实习期间）、Zhen Jia、Shuai Zheng、Zhen Zhang、Xinwei Fu（AWS）、T. S. Eugene Ng（Rice 大学）、Yida Wang（AWS）

在阅读 ByteCheckpoint（NSDI’25） 时，端到端有效训练时间率（ETTR）与平均浪费时间公式正是引自这篇 SOSP’23 论文。ByteCheckpoint 主攻面向持久存储（HDFS）的全栈高吞吐 I/O 与弹性加载时 Resharding，而 Gemini 则回答了另一个经典问题：如果把用于容错恢复的高频 Checkpoint 直接存进集群各节点的 CPU 内存并互相跨机备份，怎样排布副本最抗机器宕机？又怎样在共用同一张高速训练网络的前提下做到对正常训练零干扰？

#摘要

大模型分布式训练动辄持续数月、跨越成百上千台机器，软硬件故障极其频繁（例如 OPT-175B 在 992 张 A100 上两个月遭遇约 110 次故障，浪费了 17.8 万 GPU 小时）。传统方案将 Checkpoint 写入远端持久存储（如云文件系统或对象存储），受限于远端存储有限的聚合带宽，不仅拉取恢复动辄数十分钟，平日也不敢高频保存（如 BLOOM 每 3 小时才存一次），一旦故障就要丢掉几个小时的训练进度。

Gemini 利用现代 GPU 服务器上容量远大于显存的主机 CPU 内存以及远快于远端存储的机间训练网络，将容错恢复速度推向极致，核心解决两大挑战：

  1. CPU 内存易失性与可用性挑战：机器宕机时其内存中的副本随之丢失。Gemini 提出一种可证明最优/近似最优的混合副本放置策略（Mixed Placement Strategy），在给定副本数mmm 下最大化全部机器都能从存活节点 CPU 内存直接恢复的概率；
  2. 网络带宽争用挑战：跨机备份与正常训练集合通信共享同一张网络。Gemini 在线剖析训练通信时间线，通过小分块切分 + 多子缓冲双层流水线将 Checkpoint 流量塞进计算期间的网络空闲窗口（Idle Timespans）。

基于 DeepSpeed ZeRO-3 在 AWS EC2 A100/V100 集群上评估 GPT-2 100B 等模型表明：Gemini 将 Checkpoint 拉取时间缩短最高 250×，保存频率提升至理论最优的每步一次（Every Iteration，相比基线高 8×–170×），对正常训练迭代耗时零开销，整体故障恢复浪费时间降低超过 13×。

#1. 动机与问题建模

#1.1 故障恢复的「浪费时间」公式

同步分布式训练要求所有节点步调一致：一旦发生故障，所有机器都必须回滚到最近一份完整的 Checkpoint 重新算起。

如图 1 所示，假设每 100 步往远端存储写一次 Checkpoint，在迭代 310 时发生故障，而第 3 份 Checkpoint 尚未写完，系统只能回滚拉取迭代 200 的第 2 份 Checkpoint。作者将一次故障造成的浪费时间（Wasted Time，不含修机器/换机器本身的时间）定义为「回滚丢失的训练进度 + 拉取恢复耗时」，由三个变量决定：单次保存耗时tckptt_{\text{ckpt}}tckpt​、保存频率fff（即每隔1/f1/f1/f 秒启动一次保存）以及拉取耗时trtvlt_{\text{rtvl}}trtvl​。

#1.2 机会：用途解耦与三级内存/存储层次

作者统计了主流公有云与 DGX 机型（如 AWS p4d.24xlarge 配 8×40GB = 320GB 显存，主机内存却高达 1152GB；DGX A100 配 640GB 显存 + 2TB 主机内存），发现每台机器的 CPU 内存足以轻松放下数份分片 Checkpoint，且 GPU 节点间的训练网络（100–400Gbps EFA/RoCE/IB）单机带宽就顶得上整个远端文件系统的总带宽。

至于「CPU 内存装不下完整历史版本供迁移学习或模型回溯调试」的顾虑，Gemini 的做法是按用途解耦：

  • 容错恢复专用快照：高频写入本地 CPU 内存 + 远端对等节点 CPU 内存，只保留最新完成的一份（加一份正在写入的缓冲），对用户完全透明；
  • 归档/下游评估快照：仍按常规低频（如每 3 小时）异步写入远端持久存储；同时当极端多机同时宕机导致内存副本不全时，远端持久存储作为兜底保底 100% 可恢复。

#2. 系统架构

如图 2 所示，Gemini 由两大模块协同工作：

  1. Checkpoint 创建模块：每台训练机器运行一个 Worker Agent，初始化时根据机器总数NNN 和副本数mmm 计算好放置拓扑；训练过程中按流量交错调度算法，将本机 GPU 上的模型与优化器状态分片同时写入本机 CPU 内存（1 份本地副本）和指定伙伴节点的 CPU 内存（m−1m-1m−1 份远端副本）。
  2. 故障恢复模块：由全体 Worker Agent、唯一一个 Root Agent（共生在某台普通训练机器即 Root Machine 上）、一个分布式 KV 存储（实现中采用 etcd）以及云平台算力控制器（如 AWS Auto Scaling Group）组成。Worker Agent 周期性往 etcd 写本机健康心跳；Root Agent 巡检心跳，发现故障后按故障类型指挥原地恢复或向云平台申请替补机器；若 Root Machine 自身宕机，存活节点通过 etcd 的分布式选主（Paxos/Raft）自动提升新 Root Agent。

#3. 核心设计一：可证明近似最优的 CPU 内存副本放置

#3.1 Group vs. Ring vs. Mixed 放置策略

给定NNN 台机器和副本数mmm（每台机器必须有 1 份在本地以减少网络发送量并加速软件故障原地恢复，另发m−1m-1m−1 份到其他机器），副本存在哪几台机器上，直接决定了多机并发宕机时内存快照的存活率。

看图 3 中N=4,m=2N=4, m=2N=4,m=2、同时挂掉k=2k=2k=2 台机器的直观对比（共有(42)=6\binom{4}{2}=6(24​)=6 种双机故障组合）：

  • 分组放置（Group Placement，图 3a）：将机器两两配对成互不相交的小组 {1, 2} 和 {3, 4}，组内互存对方副本。只有当 {1, 2} 同时挂或 {3, 4} 同时挂（仅 2 种组合）时，才会丢失某台机器的全部两份副本；其余 4 种跨组双机故障都能从各自存活的搭档内存里找回完整快照，内存恢复成功率4/6=66.7%4/6 = 66.7\%4/6=66.7%；
  • 环形放置（Ring Placement，图 3b）：机器 1 → 2 → 3 → 4 → 1 顺次把副本存给左手邻居。只要任意两台相邻机器同时挂掉（{1,2}, {2,3}, {3,4}, {4,1}，共 4 种组合），其中一台的本地副本和唯一远端副本就会同归于尽！失败回退远端存储的概率比分组放置高出一倍。

那当机器数NNN 不能被副本数mmm 整除时怎么办？Gemini 提出混合放置策略（Mixed Placement，图 3c）：先分出⌊N/m⌋−1\lfloor N/m \rfloor - 1⌊N/m⌋−1 个标准mmm 机小组走 Group 策略，再把剩下的N−m(⌊N/m⌋−1)N - m(\lfloor N/m \rfloor - 1)N−m(⌊N/m⌋−1) 台机器（如图 3c 中N=5,m=2N=5, m=2N=5,m=2 时剩下的机器 3、4、5）组成一个小环走 Ring 策略，每台依然只收发m−1m-1m−1 份副本。

#4. 核心设计二：无感流量交错与双缓冲传输流水线

#4.1 在应用层统一编排两类流量

要把本机 GPU 上的分片存到远端机器的 CPU 内存，如果走「本地 GPU → 本地 CPU → TCP/RDMA 发给远端 CPU」，应用层很难精确控制网卡发包与 GPU 训练集合通信（如 ZeRO-3 每层前反向的 All-Gather / Reduce-Scatter）的抢带宽问题。

Gemini 换了一条很巧的通路：先走机间 GPU-to-GPU 通信（直接复用 NCCL）把快照发到对端机器的 GPU 临时缓冲区，再在对端机器内部做本地 GPU-to-CPU（D2H）拷贝落入主机内存。这样做的好处是训练流量和快照流量都走同一个 NCCL 层，无需底层网络 QoS 配合，就能在应用层精准利用计算期间天然存在的网络空闲窗口（图 4c）完成穿插。

#4.2 克服显存占用与接收端 D2H 气泡

直接按上述路径发整包快照会撞上两堵墙（图 5）：

  1. 接收端额外显存导致 OOM（图 5b）：GPT-2 100B 在每张卡上的状态分片高达 9.4GB，训练时显存早已被参数、梯度和激活塞满，对端 GPU 根本腾不出 9.4GB 来接整包快照。
    • 解法：预留小缓冲 + 快照分块（Partitioning）。训练中的 GPU 通常还剩几百 MB 空闲显存，Gemini 仅预留一小块通信缓冲RRR（实验默认仅 128MB），把大快照切成小块逐块发送，对端接完一块立刻 D2H 拷入 CPU 内存腾空缓冲。
  2. 接收端 D2H 拷贝造成网络空闲气泡（图 5c）：若只用单个缓冲，发送端发完第 1 块后必须干等接收端把数据经 PCIe 拷回 CPU 内存才能发第 2 块。在 AWS p4d.24xlarge 上实测机内 D2H 带宽与机间 EFA 网络带宽同为 ~400Gbps 量级，这意味着网络空闲窗口里几乎有一半时间被 D2H 等待白白浪费掉，塞不下整份快照。
    • 解法：多子缓冲乒乓流水线（Pipelining，图 5d）。将总大小为RRR 的 GPU 预留缓冲均分为ppp 个子缓冲（实验中R=128MB,p=4R=128\text{MB}, p=4R=128MB,p=4，每个子缓冲 32MB），轮流交替使用：当对端正在把子缓冲 1 的数据经 PCIe 拷往 CPU 时，机间网络可以同时向子缓冲 2 接收下一块快照，让跨机 GPU-to-GPU 传输与对端本地 D2H 拷贝完全重叠。与此同时，本机自己的那份本地副本不占机间网络，直接切块与训练集合通信重叠做本地 D2H 拷贝即可。

Gemini 在训练最开始的若干步（实现中为前 20 个迭代，不打快照）做轻量级在线剖析，给所有集合通信算子打上起止时间戳，提取出单步内稳定的网络空闲区间序列T={t1,t2,…,td}\mathcal{T} = \{t_1, t_2, \dots, t_d\}T={t1​,t2​,…,td​}（实测跨步标准差小于 10%）。

#5. 区分故障类型的分级恢复机制

传统方案不管是进程崩了还是显卡烧了，一律推倒重来去远端存储拉全量快照（图 6a）。Gemini 则将故障分为两类分别加速（图 6b–c）：

  1. 软件故障（Software Failures，图 6b）：由代码 Bug、数据异常或瞬时软件错误引起，物理机器完好、主机内存并未掉电。此时无需换机器，所有节点直接从本机 CPU 内存读取上一步刚存好的本地副本原地重启，拉取耗时几乎为零，平均浪费时间低至1.5×Titer1.5 \times T_{\text{iter}}1.5×Titer​。
  2. 硬件故障（Hardware Failures，图 6c）：如 GPU 双比特 ECC 错误、机器掉线等，Root Agent 联动云平台（或从预先热备的 Standby 备机池秒级顶上）用新机器替换坏机器，新机器继承原机器的 Rank ID：
    • 情况 1（每个放置小组内至少还有一台存活机器）：存活老机器直接读本地内存副本；新换上来的机器（如图 6c 中顶替机器 2 和机器 4 的 Machine 2' 与 Machine 4'）直接走高速机间网络从组内存活搭档（分别为 Machine 1 和 Machine 3）拉取备份到内存（注：论文 6.2 节第 1278 行正文误写为 “Machine 4’ also retrieves the checkpoint from Machine 4”，机器 4 已故障下线，对照图 6c 实际是从同组存活的 Machine 3 拉取）；
    • 情况 2（至少有一个小组全军覆没）：虽然其他存活组内存里还有新快照，但因迭代步号与远端持久存储里的旧快照不一致，全体机器统一回退到远端持久存储做一致性恢复。

此外还有一个非常真实的工程细节（§7.1 & §7.3）：Gemini 在平时每步往 CPU 内存拷快照时只做裸内存拷贝、绝不调用 torch.save() 做序列化！因为实测 torch.save() 序列化单次就要阻塞几十到上百秒；只有在真正发生故障需要恢复时，Root Agent 才通知存活节点调用一次 torch.save() 把内存里的最新完整缓冲落成 PyTorch 可加载格式，从而把昂贵的序列化开销彻底移出了日常无故障训练路径。

#6. 实验评估

实验基于 DeepSpeed v0.7.3（ZeRO-3）+ PyTorch 1.13 + etcd v3.5 实现，主力测试床为 16 台 AWS p4d.24xlarge（共 128 张 A100-40GB，单机 1152GB 内存，机间 400Gbps EFA 网络；远端持久存储采用聚合带宽 20Gbps 的 AWS FSx），另在 16 台 p3dn.24xlarge（128 张 V100-32GB，100Gbps 网络）验证泛化性。模型覆盖 10B–100B 的 GPT-2、RoBERTa 与 BERT（Adam 优化器 + 混合精度 + 激活重计算）。

对比两个远端存储基线：Strawman（仿照 BLOOM 每 3 小时存一次 FSx）与 HighFreq（打满远端存储带宽的极限频率，每隔⌈tckpt/Titer⌉\lceil t_{\text{ckpt}} / T_{\text{iter}} \rceil⌈tckpt​/Titer​⌉ 步存一次 FSx；对 GPT-2 100B 为每 9 步一存）。

#6.1 正常训练零干扰与浪费时间骤降

  • 迭代吞吐零损失：在 128 张 A100 上训练 GPT-2 / RoBERTa / BERT 三个 100B 模型并开启每步 Checkpoint（GPT-2 100B 单步迭代 62s，Gemini 单次快照传输不到 3s），单步耗时与完全不开 Checkpoint 的原生 DeepSpeed 几乎分毫不差，塞完双副本流量后网络仍有富余空闲时间；
  • 平均浪费时间降低 >13×（图 10）：Strawman 每次故障平均浪费近 100 分钟，HighFreq 也要 20 多分钟；而 Gemini 在软件故障（替换 0 台）时仅浪费1.5Titer1.5 T_{\text{iter}}1.5Titer​，替换 1 台或替换 2 台但命中内存恢复（占 93.3% 概率）时跨机拉取不到 3 秒，比理论最强的远端存储方案 HighFreq 还要快 13 倍以上；
  • 聚合带宽随集群线性扩展：远端存储带宽固定为 20Gbps，机器越多基线也没法变快；Gemini 利用机间网络聚合带宽，16 台机器在 100Gbps 网络下快照耗时缩短 65×，在 400Gbps 网络下缩短超过 250×（远端存储要想追平，理论上需要提供 6.4Tbps 的聚合读写带宽），快照频率相比 HighFreq 提升 8×、相比 Strawman 提升 170× 以上。

#6.2 真实故障恢复全链路耗时拆解与千机模拟

作者在图 14 中诚实地拆解了一次真实触发单机故障后的全部端到端停机开销（超出纯 Checkpoint 浪费时间的部分）：

  1. 心跳故障检测：15s；
  2. 存活节点执行按需 torch.save() 序列化（含本地与远端两份副本）：162s；
  3. 云平台 ASG 申请新 p4d 实例等待：4–7 分钟（若配置热备 Standby 机器可直接省去）；
  4. Checkpoint 跨机拉取：< 3s；
  5. 重启预热（Restart Warmup，建通信组与 CUDA 初始化等）：253s。

合计下来，软件故障总停机约 7 分钟，无热备机的硬件故障约 12 分钟。在此实测参数基础上做大规模模拟（论文图 15）：

  • 高频故障场景（每日 8 次故障）：Gemini 的有效训练时间率（ETTR）紧贴无故障理想线；反观 HighFreq，哪怕一次故障都不发生，光每 9 步调一次 torch.save() 阻塞的 81 秒序列化开销就白白吃掉了 14.5% 的训练时间；
  • 千机规模扩展（1,000 台实例 = 8,000 张 GPU，按 OPT 报告设日故障率 1.5% 即每天 15 次故障）：Strawman 因故障间隔比回滚丢失时间还短，训练几乎原地踏步无法推进；HighFreq 的 ETTR 跌至约 59%；而 Gemini 依然维持在 ~91% 的 ETTR（高出 HighFreq 54%）。

#读后总结

把 Gemini（SOSP’23）、MegaScale（NSDI’24） 和 ByteCheckpoint（NSDI’25） 三篇放在一起读，能清晰看到大模型容错基础设施近三年的演进拼图：

  1. 「热恢复走集群内存 + 冷归档走远端存储」的分级思想已经成为行业共识。Gemini 算清楚了一笔硬件账：GPU 服务器的本地 DRAM 容量是显存的 2–3 倍，机间 RDMA 网络聚合带宽是共享存储的百倍以上，把每步容错快照留在计算集群内部消化，才能突破远端存储带宽天花板做到 per-iteration 零丢失回滚；
  2. 「成组互备优于环形链式」是一个普适的分布式副本放置结论。直觉上很多人会随手写成 rank i → rank (i+1)%N 的环形备份，以为负载最均匀；但 Gemini 用极简的组合证明指出，环形放置产生了NNN 个相异故障脆弱集，而两两/多机闭环分组把脆弱集压缩到了最优下界N/mN/mN/m，不改硬件、不多花一字节内存就把双机并发掉线的数据丢失率砍掉一半；
  3. 图 14 暴露的「非传输瓶颈」恰恰指明了后续系统的优化靶心。当 Gemini 把快照保存与拉取本身压到 3 秒以内后，图 14 里真正占大头的变成了 162 秒的 torch.save 序列化和 253 秒的重启预热（建组等）——而这恰恰就是后来 MegaScale 用 Redis 去屏障把建组压到秒级、ByteCheckpoint 用零拷贝二进制分片流式异步落盘消灭 torch.save 阻塞、以及弹性训练框架解决「少几台机器无热备时加载时 Resharding」所接力攻克的地方。
